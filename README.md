# The Whiteboard Room

A Godot 4 explorable knowledge-products office with reception, specialist
workspaces, upstairs departments, and a conference room. The Projects / Research
hub has three live screens: Excalidraw at https://draw.homehub.tv/ on the central
wall opposite the entrance, HomeHub at https://homehub.tv/ on the former
Excalidraw wall, and OpenCode at https://opencode.homehub.tv/. The former
courtyard is no longer part of the active world.

## Controls

- **WASD**: walk; **Shift**: run; move the mouse to look.
- **Space**: jump. Double-tap Space to toggle flight; hold Space to rise and C to
  descend. Flight moves at twice the running speed. Jumping carries horizontal momentum; you can
  retain takeoff direction and speed in the air, and can jump again after landing on a wall.
- Get within 12 room units of a browser board, aim at it and **click** to
  use it in place. The camera stays still while you move the cursor and draw;
  keyboard input goes to the board. Hold the **right mouse button** to look around,
  and release it to return to the cursor. **Esc** returns to room navigation.
- While navigating, aim at a browser board and press **E** from anywhere in the room for its full-window
  view; **Esc** returns to the room. Press Esc before E if already using the wall,
  since E is sent to the browser in wall mode.
- While navigating, aim at a browser board and press **Shift+E** to return it to
  its default URL. Press Esc first if the browser has focus; Shift+E remains normal
  text input there. This navigates away from the current page and may discard unsaved work.
- You start in reception, which connects to the Specialists,
  Departments, and Projects / Research wings. Specialist offices are organized
  around duties, with the account manager first on the left and the project
  manager at the end of the corridor.
- Outside the board, **Esc** releases the mouse cursor; press Esc again or click
  the room to capture it.

The 3D board displays the same embedded browser as the full-window view. The
viewport is configured for 2560×1440. Each browser board has its own live page.
The embedded browser requests up to 120 updates per second; actual update and
game frame rates depend on rendering load and display synchronization. Adjust
`BROWSER_FRAME_RATE` near the top of `main.gd` if needed. The current gdCEF
version cannot change this limit at runtime, so distant boards are not yet
throttled to 1 FPS. The 3D viewport is disabled while the full-window view is open.

## Comfort settings

The root node exposes `horizontal_fov` (default 90 degrees), `look_smoothing`
(default 25; set to 0 for direct mouse input), and `wall_brightness` (default
0.88). Adjust these in the Godot inspector or at the top of `main.gd`. Smoothing
may feel laggy to some people; the board tint affects only the wall texture,
not the full-window browser. Take a break if the room causes discomfort.

The camera interpolates between physics ticks while
mouse look remains per-frame, to avoid judder on high-refresh displays.

## World scale and building on the project

One Godot unit is one meter. The camera sits at a 1.7 m eye height; the active
boards are 3 × 1.6875 m, mounted in the research hub.
They're deliberately large surfaces, not desktop monitors. The default jump
reaches roughly 5 m above the starting eye position; change `jump_speed` on the
root node or in `main.gd` to tune it. Flight remains available by double-tapping
Space. The player collides with the office's walls and furnishings.

`main.gd` coordinates the room, browser lifecycle, and interaction transitions.
Room action names are in `scripts/room_input.gd` and their default bindings are
editable in Project Settings → Input Map. Movement lives in
`scripts/player_movement.gd`, interaction modes in `scripts/interaction_state.gd`,
and browser mouse translation in `scripts/browser_input.gd`. Browser keyboard
events are forwarded separately, so room shortcuts do not intercept typing.
The browser-board construction helper and URL constants live in
`scripts/browser_boards.gd`; active board placement is configured in `main.gd`. The currently supported
board geometry is a vertical rectangle facing local +Z. The `CommunityAssets`
node in `main.tscn` is an
editor-visible place to instance models and other scene content without editing
the generated room.

The office is a separate packed interior in `scenes/office_interior.tscn`,
instanced as the active world. Its simple modular geometry is generated by
`scripts/build_office.gd`. The specialist corridor shares offices for the account
manager and delivery lead, the consultant and knowledge specialist, the website
developer and content/design specialist, and the two developers. The project
manager has an individual office. These use the same workstation
layout as the upstairs offices.
Projects / Research is an unstaffed octagonal hub with two open spokes, live
browser screens and additional placeholders. An enclosed, three-metre-wide stair
route with a single flight and landings leads from reception to the second-floor
Departments. Sales and Customer Support share the bullpen in tall, single-entry
cubicles. Sales and support managers share a four-person office with marketing and
the product manager. IT, engineering and operations share an expanded office on
the north row, next to HR/legal; the CFO and COO remain on the opposite
side of the bullpen. Shared offices have divided workstations and
bullpen-facing data boards. A smaller
glass-fronted conference room connects directly to the CEO's private office,
which also opens into the bullpen. A receptionist placeholder stands behind the
reception desk. Figures and placeholder monitors do not have their own interaction yet. The
Interiors A archive has not been adopted into this scene.

`OFFICE_PLAN.md` records the hypothetical knowledge-business headcount and
revenue-per-employee scenarios. It does not represent a financial forecast.

### Employees and locations

`data/employee_roster.tres` is the editable list of 29 fictional employees.
Each record has a numeric `id`, display name, description, department, and room.
IDs identify employees and their future agents: never change or reuse an ID for
another employee. Department identifies peers; room determines where someone
works. They are independent, so colleagues can work in different rooms and a room
can contain several departments.

Individual labels show display names and face the camera, without a
PLACEHOLDER suffix. In the sales and customer support bullpens, only the central
team labels are shown; these also face the camera.

The office builder tags each desk marker with a `room` and a unique `desk_number`
within that room. Regenerate the office with
`godot --headless --path . --script res://scripts/build_office.gd` inside the
preview shell after changing its builder.

At startup `EmployeeDirectory` assigns employees in numeric ID order to desks
in desk-number order within their room. If a room runs out of desks, a warning
identifies each unplaced employee; other employees still spawn and all remain in
the roster. Assignments can change when the roster or desks change.
`get_employee(id)` returns a definition and `get_character(id)` returns the live
node; its `global_position` is the current world position. Unknown or unplaced
characters return null. `roster.desired_agents()` returns every employee ID in
numeric order, independent of roster order. This is an inventory only: no AI
backend, communication rules, movement, or employee-state persistence exists yet.

### Add a community asset or plugin

1. Try candidates in ignored `assets/_scratch/`. Follow `assets/README.md` to
   promote assets used by shared scenes or scripts, including placeholders.
   Check license, access and redistribution terms, and record provenance.
2. For models, prefer glTF 2.0 (`.glb` or `.gltf` plus its dependencies). Put
   source files under `assets/<asset-name>/`, open the project in Godot, and let
   the editor import them. Instance the imported scene under `CommunityAssets`
   in `main.tscn`, set its position and scale in meters, and save the scene.
3. For an editor plugin, follow its install instructions (usually an `addons/`
   directory and Project Settings → Plugins). Review scripts and native binaries
   before enabling them; plugins execute code in the editor. Commit the plugin
   files and any required project configuration only when its license permits it.
4. Keep Godot's `.import` sidecar settings and project-owned or modified source
   in Git. Unmodified adopted downloads are pinned in `assets/downloads.nix`;
   generated `.godot/` files stay ignored. Add new files to Git before evaluating
   the Nix flake, since Git-backed flakes only include tracked or staged files.
5. Run the headless and browser checks below, then inspect the scene interactively
   on the target desktop for scale, lighting, performance, and comfort.

**Your existing drawings may not appear automatically.** The embedded browser has
its own persistent profile under Godot's user data directory; it does not share
local browser storage or logins with your usual browser. The supplied homepage
can therefore show a blank canvas. A shareable board or collaboration link may
provide access to the same drawing; see [World scale and building on the project](#world-scale-and-building-on-the-project)
for URL configuration. Back up important work: browser-local storage is not the
same as a NAS-side board database.

## Shared checkout and running on Beast

This checkout is shared with the NAS. Edit source from either machine, but run
Godot, project Nix shells, direnv reloads, imports, and tests on Beast only; from
the NAS use `ssh beast` first. The shared `.godot`, `.direnv`, and `cef_artifacts`
are not safe to initialize using a different machine's Nix store. Do not run two
editors on this checkout at the same time. Use an isolated copy on Beast for
checks while the checkout is in use.

Open a terminal in your desktop session:

```sh
cd ~/Projects/godot-3d-starter
nix develop
godot --path .
```

If you already have an older `nix develop` shell open, exit it and enter a new
one first. The first build downloads the pinned gdCEF release (about 1 GB),
its extension sources and CEF build dependencies, and builds the patched extension
and a Godot editor with a shared C++ runtime; compiling them can take many minutes. The project creates an ignored `cef_artifacts` symlink to the Nix store.
It will not overwrite an existing non-managed file or directory at that path.

Use the Godot from this shell, including for the editor (`godot --editor --path .`):
the standard Nixpkgs Godot's static C++ runtime conflicts with gdCEF on shutdown.
The project prefers native Wayland on Linux and falls back to X11 when Wayland
is unavailable. To force X11 for troubleshooting, run
`godot --display-driver x11 --path .`. This project setting affects the game;
the editor's display server is configured separately in Godot's editor settings.
The current gdCEF browser still requires an X11 display (usually XWayland) even
when the Godot window itself runs natively on Wayland. Without one, the embedded
browser fails to initialize and the project falls back to its preview behavior.

If gdCEF fails to initialize, each board opens its URL in the system browser;
the Excalidraw board also uses a periodically refreshed screenshot when `chromium`
is on PATH. For a
preview-only environment that does not provision gdCEF, run `nix develop
.#preview` instead. The preview shell uses the same shared-C++ Godot build so
that an existing gdCEF extension can be discovered safely.

## Verify

### Godot AI MCP

The project configures the MIT-licensed [Godot AI](https://github.com/hi-godot/godot-ai)
editor bridge for OpenCode. From the project root, enter `nix develop` and run
`godot --editor --path .`. The shell links the pinned editor add-on into
`addons/godot_ai`; it will not overwrite an existing add-on at that path. The
plugin is enabled in `project.godot`. Leave the editor open, then connect or
restart OpenCode and check `/mcps` for `godot-ai`. Ask the agent, for example,
to inspect the current scene hierarchy. The plugin is inactive in headless mode.

OpenCode starts the stdio bridge automatically. The add-on and bridge use
authenticated local connections on ports 8000 and 9500 by default. Their tools
can modify project files and run the project; use them only in a trusted local
environment. Anonymous telemetry is disabled by the project shell and bridge.
The add-on source is locked by Nix; the bridge uses `uvx` to download the matching
version 4.3.1 Python package and dependencies from PyPI on first use. Those
downloads are version-resolved by uv, not fully hash-pinned by the flake.

Do not use the add-on's in-editor updater on the Nix-store symlink. Upgrade the
flake pin and matching bridge version together instead. If an existing add-on
conflicts with the symlink, the shell leaves it untouched and reports a warning.

For a non-graphical smoke test:

```sh
nix develop .#preview --command bash scripts/verify.sh
```

This imports the project, checks GDScript files, runs the room, movement,
input-state, employee, and office smoke tests, and briefly starts the main scene. It does not exercise gdCEF or
replace an interactive visual check. The project uses GDScript and Godot 4.7.2
stable, pinned through `flake.lock`.

The browser integration test requires network access to the Excalidraw URL and
uses a temporary, isolated browser profile. It starts a local HTTP fixture and
checks rendering, focus, mouse and keyboard input, persistence across launches,
and clean shutdown under Xvfb:

```sh
nix shell nixpkgs#python3 nixpkgs#xvfb-run --command nix develop --command python tests/run_browser_smoke.py
```

The Nix package rebuilds the gdCEF Godot extension with a period-key mapping
fix, retaining the pinned upstream CEF runtime and render subprocess. The
browser integration test includes punctuation input without exclusions.
